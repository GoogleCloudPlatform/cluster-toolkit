# Command and Control of Clusters
Previous versions of OFE relied on the OFE webserver instance being able to SSH directly to clusters in order to perform command and control (C2) operations. When clusters were created, an admin user was set that would accept a public ssh key for which the webserver owned the private key. This was largely straightforward, and worked quite well. The clusters were also able to make HTTP API queries to the webserver.

This works well in the case where webserver and clusters all have public IP addresses, and are able to receive inbound requests, but it breaks down in the case where a user may wish to have the compute clusters not be directly exposed to the public internet.

The new approach is based around [Google PubSub](https://cloud.google.com/pubsub/). The webserver and clusters now no longer directly communicate via SSH and HTTP, but rather send messages via Google Cloud. This offers the advantage of supporting clusters that are not publicly accessible, and removes the reliance on SSH connections between webserver and clusters.

## PubSub details

During deployment of a new OFE system, a new Google PubSub Topic will be created.  This centralized topic is used for all command and control traffic between the OFE webserver and the client clusters. Individual Subscriptions are created for each cluster controller, as well as for the OFE itself.  The OFE creates a new subscription for each cluster, and informs the cluster that it is to use the newly-created subscription.

![PubSub data flow](https://cloud.google.com/pubsub/images/wp_flow.svg)

### Message Delivery

Each [subscription is filtered](https://cloud.google.com/pubsub/docs/filtering) based off of a message attribute.  Messages to each Cluster **MUST** have an attribute `target=cluster_X` where `X` is the Cluster's unique ID. Messages to the OFE **MUST NOT** have a `target` attribute.

By using filtering in this way, and having a 1:1 mapping between Subscription and Recipient, we guarantee that the messages being sent are received by only the intended recipient.

### Message Schema

Beyond the filtering attribute requirements previously discussed, the form of the messages are as follows:

#### Common Attributes

* `command` - The command being sent as part of the message
* `source` - The identity of the sender - corresponds to the `target` attribute. This is how the OFE identifies which cluster sent the message

#### Common Message Data

* `ackid` - A UUID generated by the system to identify a command/response pair.

Each command will have additional data in the Message Data, specific to that command's requirements.

#### Commands

The command is carried in the `command` message attribute. Directions are
from the registered handlers in `website/ghpcfe/cluster_manager/c2.py` (the
OFE) and `ghpcfe_c2daemon.py` (the cluster daemon).

| Command | Direction | Purpose |
| ------- | --------- | ------- |
| `ACK` | both | Acknowledges a previous command by `ackid`; signals that the command is complete. |
| `UPDATE` | both | Progress for a previous command by `ackid`; the command is not yet complete. Can be sent several times, then followed by an `ACK`. The OFE sends it to deliver the `verify_key` during `REGISTER_USER_GCS`. |
| `PING`, `PONG` | both | Testing commands, answered with a `PONG` carrying the same `id`. Not typically used. |
| `CLUSTER_STATUS` | cluster to OFE | Reports a change in the status of the cluster, for example that it has finished initialisation and is ready for jobs. |
| `SYNC` | OFE to cluster | Synchronise with the OFE: upload log files and re-download and run the Ansible setup. |
| `SPACK_INSTALL` | OFE to cluster | Install a Spack package by submitting a Slurm job. |
| `INSTALL_APPLICATION` | OFE to cluster | Install a custom application by submitting a Slurm job that runs the supplied install script. |
| `RUN_JOB` | OFE to cluster | Submit a job on behalf of a user to Slurm. |
| `REGISTER_USER_GCS` | OFE to cluster | Begin registering a user's GCS credentials via an interactive `gcloud auth login` flow (credentials are shared with `gcloud storage`). |

### Topic and subscriptions

All names are prefixed with the deployment name, which is also the topic name.

| Resource | Name | Filter | Created by |
| -------- | ---- | ------ | ---------- |
| Topic | `<deployment_name>` | none | Terraform (`tf/main.tf`) |
| OFE subscription | `<deployment_name>-c2resp` | `NOT attributes:target` | Terraform; the OFE creates it if missing |
| Cluster subscription | `<deployment_name>-cluster_<id>` | `attributes.target="cluster_<id>"` | The OFE, when a cluster is created |

Separately, Terraform creates a topic `<deployment_name>-build-logs`, a logging
sink and a subscription `<deployment_name>-build-logs-sub` for Cloud Build
logs, which the OFE uses to track container image builds. These are not
part of the cluster command and control channel.

### Cluster C2 Daemon

During startup of a cluster, a Daemon is installed which creates a Streaming Pull thread to Subscribe to the Cluster's Subscription.  This daemon is responsible for responding to C2 messages and following through on the message's requests, including submitting jobs to SLURM to install Spack packages, and run user's jobs.

### Security

The C2 topic and the OFE's subscription are created at deployment time. The OFE creates one subscription per cluster.

When a cluster is created, the OFE grants the cluster's controller service account `roles/pubsub.subscriber` on **that cluster's own subscription**, and `roles/pubsub.publisher` on the **C2 topic** (`setup_service_account` in `c2.py`). These are the only resource-level Pub/Sub bindings the OFE adds. Separately, the cluster blueprint template creates a service account with project-level roles, including `pubsub.admin` and `resourcemanager.projectIamAdmin` (`hpc_service_account` in `website/ghpcfe/templates/blueprint/cluster_config.yaml.j2`).

Sadly, the OFE's Service Account must have either the role of `pubsub.admin` or a custom role, set at the project level.  This is because creating subscriptions and setting IAM Policy Bindings are actions done at the project level, rather than attached to the topic.

By setting IAM policy bindings, we are able to grant permissions to service accounts which are associated with clusters which are in projects other than the base project where the OFE resides.

For example, if the OFE is in GCP Project `Alpha`, the C2 Topic will also be in Project `Alpha`.  If a cluster is then created in project `Beta`, the OFE will grant the cluster's Service Account IAM permissions within the `Alpha` project.

## Data Storage

Clusters automatically upload job logs to a GCS bucket, which is specified at cluster creation time.  The Cluster's Service Account is granted ObjectAdmin permissions in order to create and update Log files in the GCS bucket.

The OFE webserver displays log files from the GCS bucket.
